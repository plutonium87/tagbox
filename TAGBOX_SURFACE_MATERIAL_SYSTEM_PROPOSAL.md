# Tagbox Surface Material System Proposal

## Scope and evidence labels

This is an architecture study only. **Verified** statements below describe the current repository. **Proposal** statements are recommendations for a later implementation; they do not describe existing behavior.

## 1. Current architecture findings

### Surface assets and coordinates — verified

- `src/surfaces.ts` loads custom surfaces registered in `/surfaces/manifest.json`. Each surface has a `surface.json`, positive logical `width`/`height`, required background, and optional foreground and paint mask. Paths resolve relative to `surface.json`.
- Background, foreground, and paint mask use the same `fit` transform (`stretch` by default, `contain`, or `cover`). Paint masks are rasterized to the surface's logical dimensions before use.
- The Norrtåg and City park surfaces are 3240×1080 in their current JSON configurations. Built-in Solid and Steel Gate use 1920×1080. Viewport/DPR scaling is separate from logical drawing coordinates; PNG export uses the active logical dimensions.
- `CustomSurfaceDefinition.maps` exists as a compatibility field, but `maps` entries are not loaded or consumed. The surface asset README explicitly says there is no separate paint-opacity map and that roughness/normal maps are not implemented.
- Missing or failed optional paint masks result in unrestricted paint. A custom surface with an absent or failed material map should follow an analogous fallback, but material handling does not currently exist.

### Paintability — verified

- `buildLogicalPaintMask` creates a logical-size canvas. Grayscale mode uses red × source alpha; alpha mode uses alpha; optional foreground alpha further gates the mask. Thus paintability is a continuous scalar, not just a binary region.
- `main.ts` passes the selected surface's mask to `CanvasRenderer.setPaintMask`. The renderer uploads it as RGBA8 and binds it for Marker, Spray, and runoff shaders. Those shaders multiply fragment coverage/deposition by the sampled mask. No mask is equivalent to full paintability.
- Foreground display/export compositing is a separate canvas layer. Norrtåg has a special export order. Material identification must not be merged into that foreground, paintability mask, paint-opacity behavior, or paint layer.

### Deposition and rendering — verified

- `BrushEngine` in `src/brush.ts` produces Marker dab records on the CPU; dab coverage, shape, and mask multiplication occur in `baseFragment` in `src/renderer.ts`.
- `SprayEngine` in `src/spray.ts` creates deterministic particle records on the CPU. `sprayFragment` computes each particle fragment's falloff and multiplies by paintability.
- Marker runoff is generated by `RunoffEngine`; runoff geometry also passes through a shader that samples paintability.
- WebGL2 is required. `CanvasRenderer` owns RGBA8 textures/framebuffers for the paint result, three Chrome masks, and the paint-mask texture. Textures currently use LINEAR min/mag filtering and CLAMP_TO_EDGE. The renderer replays operations for undo/clear and surface changes; completed Spray particle buffers are cached on GPU.
- Chrome is currently silver, copper, or gold. Marker and Spray draw their deposits into per-kind mask framebuffers; a later fullscreen pass composites a stylized studio reflection or the loaded environment texture over the paint result. Chrome rendering is therefore coverage-mask based, distinct from ordinary paint color output.
- Existing stroke records carry tool/material identity and deposits, not sampled surface-material identity. This keeps their data independent of the selected surface but implies the material decision is made at render time.

## 2. Proposed material-map format and encoding

### Configuration and asset

**Proposal:** Add an explicit optional `materialMap` string to `CustomSurfaceDefinition` and `materialProfiles` (or equivalent profile reference) to `surface.json`. Do not overload `paintMask`, foreground, or a generic image layer. The already tolerated `maps` field could remain for compatibility, but a named `materialMap` property is clearer and makes the format discoverable. Load it with the same relative asset URL rules as other custom assets.

Create a logical-size, single-channel 8-bit label texture from the supplied image, using the same `fit` geometry as surface image and paint mask, but with smoothing disabled. Do not composite foreground alpha into the material map; transparent/outside values are handled separately by paintability and surface geometry.

### Encoding

The proposed 0/64/128/192/255 values are workable as byte labels but should be treated as categorical codes, not grayscale intensities. Reserve 0 as `unassigned`/fallback and use stable IDs for named profiles (e.g. 16 painted metal, 64 glass, 112 rubber, 160 bare metal, 208 plastic). The exact IDs are file-format decisions; avoid making IDs depend on material order or interpreting intermediate numeric values as blends. If retaining the proposed values is important for authoring tools, reserve 0 for painted metal and define an explicit fallback for unknown IDs; however, 0 then cannot represent “unassigned”. A palette/legend in the surface asset documentation is required either way.

**Sampling rule:** Upload as normalized `R8`/`RED`/`UNSIGNED_BYTE` (or RGBA8 fallback if a target/browser path proves necessary), with `NEAREST` minification and magnification. Use integer texel addressing (`texelFetch` after clamped logical pixel conversion) or an equivalent nearest lookup. Do not use LINEAR filtering: at boundaries it creates values between IDs and could select the wrong profile. Do not mipmap label maps. For resized logical maps, use nearest-neighbor resampling. Define one consistent texel-center and Y-origin convention and validate it against paint-mask sampling; current texture upload flips canvas images and shader coordinates differ by path, so this alignment deserves explicit tests.

An alternative future format is a true integer texture (`R8UI` plus `usampler2D`), which makes categorical semantics explicit, but normalized R8 with nearest sampling is simpler and sufficient for five labels. If the map grows beyond 255 labels or needs packed metadata, revisit the format rather than prematurely adding channels.

## 3. Material profile structure

**Proposal:** Keep profile identity separate from profile response. A surface map stores a stable profile ID; profile definitions can be shared across surfaces and may be built-in defaults with surface overrides. For example:

~~~json
{
  "materialMap": "material-map.png",
  "materialProfiles": {
    "painted-metal": { "id": 16, "deposition": 1.0 },
    "glass": { "id": 64, "deposition": 0.55 },
    "rubber": { "id": 112, "deposition": 0.8 },
    "bare-metal": { "id": 160, "deposition": 0.9 },
    "plastic": { "id": 208, "deposition": 0.85 }
  }
}
~~~

A practical typed profile could grow to:

- `id`: stable byte label.
- `depositionMultiplier`: scales deposited amount after paintability is known.
- `opacityMultiplier`: optional independent visual alpha response; do not conflate it with paintability or deposition.
- `roughness`, `reflectivity`: future visual response values, likely normalized 0–1 with documented meaning.
- `colorResponse`: future tint/albedo response, preferably a constrained multiplier or named response rather than arbitrary shader source.
- `chrome`: future per-Chrome behavior, such as `allowed`, `coverageMultiplier`, `reflectionIntensity`, and `roughness`/blur response.

**Version one should implement only stable ID lookup, fallback behavior, and one `depositionMultiplier` per profile.** It should first scale fragment alpha/coverage for paint materials and the Chrome mask coverage, with paintability multiplied independently. Keep `opacityMultiplier` out until its distinction from deposition is specified against the existing alpha compositing model. Roughness, image-space blur, color response, refraction, and surface-specific reflection should be later work.

For profile reuse, prefer a shared built-in profile registry keyed by stable names/IDs plus per-surface references or overrides. Avoid copying slightly different profile objects into every surface JSON. Surface-local ID-to-profile mapping remains useful because authors may assign different IDs in their source image, but IDs must map unambiguously to profile names.

## 4. Rendering integration points

1. **Load and expose:** Extend the custom surface definition/loaded record and add a getter for material map/profile data. Leave `getSurfacePaintMask` and its semantics untouched. Missing/unloadable maps yield a null map and neutral profile response.
2. **Upload/selection:** Add a distinct renderer texture and `setMaterialMap(...)`, called beside `setPaintMask(...)` from `updateSurface`. Do not route material IDs through `setPaintMask`.
3. **Marker:** Bind the material texture in `drawBaseDabs`; in `baseFragment`, derive a clamped logical texel from the fragment's logical coordinate, sample the ID, resolve the deposition multiplier, then compute effective coverage as the existing dab coverage × paintability × deposition multiplier. Keep shape/paintability tests intact. For Chrome Marker dabs, apply the same effective coverage while writing the Chrome mask, before the existing composite.
4. **Spray:** Bind the same material texture in `drawSprayBuffer`; in `sprayFragment`, sample at each fragment's surface location and scale density/falloff contribution by profile deposition, in addition to the existing paintability multiplication. Chrome Spray uses the same mask path and needs identical ID/profile interpretation.
5. **Runoff:** The question names Marker/Spray, but Marker runoff is a continuation of deposited paint. Decide whether it inherits the originating material response. The least surprising initial rule is to sample the map for runoff fragments as well, while leaving its geometry and paintability gating in place. This needs explicit product validation because runoff may cross material boundaries.
6. **Chrome composite:** First version can alter Chrome mask coverage per surface profile. Later versions may sample the material map in `chromeFragment` / `environmentChromeFragment` and choose reflection intensity, tint, or roughness per surface material. Avoid blurring or roughness work in the first release: it changes fullscreen cost and needs a defined coordinate/filtering strategy.
7. **Undo, clear, resize, export:** Keep material data out of stroke history. It is a selected-surface render input, just like paintability. Replays after surface changes use the selected surface map; current surface changes clear strokes. PNG export should continue to export only the final composited visual layers and never include the ID map as a layer. Confirm replay and undo with a map enabled.

Material lookup belongs primarily in GPU fragment shaders. That is where the renderer already knows the affected output pixel and samples paintability; CPU-side lookup would require copying map pixels into JS, additional per-dab/per-particle work, and awkwardly approximate coverage for wide/soft Spray fragments. CPU preprocessing is appropriate for validation, logical-size resampling, and profile-table construction, not per-fragment deposition. If a later feature needs material identity in saved stroke metadata or UI feedback, add a separate low-frequency CPU query path rather than moving deposition off GPU.

## 5. GPU and memory considerations

A logical R8 material texture costs approximately `width × height` bytes, excluding driver alignment/metadata: 3.32 MiB at 1920×1080 and 3.34 MiB at 3240×1080. RGBA8 would cost four times as much: 7.91 MiB and 13.35 MiB respectively. Current GPU surface paint mask is RGBA8, so a single-channel material texture can save memory if supported consistently. The source PNG and temporary logical canvas may consume additional CPU/browser memory during loading; release references to intermediates where practical.

The texture stays at logical surface dimensions; shader lookup maps the current fragment to that logical space, so viewport size and DPR do not require another copy. Per-fragment cost is one label fetch plus a small profile lookup/multiplier. A five-branch constant lookup is likely adequate; a small 1D profile texture or uniform arrays scale better if profiles grow. Avoid profile texture overengineering before profiling.

The output framebuffer remains at canvas backing dimensions. Material-map memory does not multiply with DPR if it remains logical-size, though fetch count scales with rendered fragments. Existing Chrome already maintains three backing-size RGBA8 masks, which dominate at high DPR; adding one logical-size R8 map is modest relative to those. Profile and benchmark on a representative large surface and high-DPR display.

## 6. Compatibility with surfaces and tools

- No `materialMap`: bind a neutral fallback or set `u_hasMaterialMap=0`; multiplier is exactly 1.0, preserving existing appearance and interaction.
- Invalid/unreadable map: same neutral fallback, with a diagnostic path appropriate to current loader behavior. Do not make the entire custom surface fail to load because its optional material map is unavailable.
- Unknown ID: use an explicit neutral default profile, never infer a profile from numeric closeness.
- Paintability remains authoritative: blocked mask pixels remain blocked regardless of their material ID. Effective deposition is paintability × material response; material maps cannot grant permission to paint. Foreground alpha remains folded only into paintability according to current configuration.
- Paint opacity remains a distinct future input. A material multiplier must not be silently described as an opacity map.
- Existing Marker, Spray, Chrome, undo, clear, and PNG behavior remain unchanged for surfaces without a map. With a map, intentional behavior changes are limited to configured profile effects. Solid and Steel Gate currently have no custom surface JSON; Norrtåg and City park do, but none of the current surfaces configure material maps.
- Different logical dimensions are supported by the same coordinate transform used for paintability. Material map source dimensions may differ; the loader should align it to logical dimensions with categorical nearest resampling, not the paint-mask builder's smoothing-enabled path.

## 7. Phased implementation plan

1. **Format and authoring contract:** Specify IDs, reserved/unknown behavior, profile schema, dimensions, orientation, fit rules, and sample PNG guidance. Update only documentation/config schema in the future implementation task.
2. **Optional loading and neutral rendering:** Load map separately, normalize to logical-size nearest data, upload dedicated R8/nearest texture, and test absent/failed/unknown labels. Verify all existing surfaces are pixel-equivalent when no map is present.
3. **Deposition response:** Add a GPU lookup helper shared semantically by Marker, Spray, runoff, and Chrome mask writes. Implement `depositionMultiplier` only. Ensure paintability multiplies rather than being replaced by the material response.
4. **Profiles and validation:** Add shared profiles and surface references/overrides, validate duplicate IDs and unknown references, and make asset authoring errors visible without breaking fallback.
5. **Visual surface responses:** Separately design and profile color, reflectivity, roughness, and Chrome reflection behavior. Add only properties with clear visual semantics and acceptable performance.

## 8. Risks, unknowns, and testing requirements

### Risks and unknowns

- Current paint-mask coordinate conventions vary among dab, Spray, and runoff shaders (including framebuffer Y orientation). A new map can be consistently wrong or differ between tools unless its orientation is tested with hard boundaries and asymmetric test patterns.
- Canvas 2D decoding/resampling of indexed or grayscale PNGs must preserve intended labels; normalize into a deliberate 8-bit channel and avoid color management or interpolation changing categorical values.
- Actual WebGL support/performance for `R8` upload and shader sampling should be checked on supported browsers/devices. RGBA8 is a safe fallback at a fourfold memory cost.
- Surface map edge authoring needs a documented rule. Nearest sampling prevents interpolated IDs but creates a crisp material boundary; painted material boundaries can be antialiased only by adding an explicit coverage/weight channel in a future format, not by linear filtering IDs.
- Chrome's fullscreen compositor sees the Chrome coverage masks and surface UVs; whether reflection response should follow the underlying physical material, the selected Chrome type, or both is a product/design decision.
- Runoff can cross labels. It needs a clear policy: react to destination surface per fragment (recommended first behavior) or retain source deposit response.
- Replays rely on current selected-surface inputs and operation history. Ensure active strokes, undo and surface switches do not retain stale texture state.

### Required tests for a later implementation

- Loader: missing, valid, malformed, and failed material map; relative paths; source maps smaller/larger than logical size; each fit mode; absent profiles and unknown IDs.
- Encoding: all labels survive upload; boundary pixels resolve only to a declared ID; no LINEAR/mipmap contamination; orientation/texel-center verified with asymmetric labels.
- Independence: black paintability under a nonzero material stays blocked; zero/unassigned material on a paintable pixel gets neutral response; foreground-alpha gating remains unchanged.
- Tool parity: Marker shapes, Spray standard/calligraphy, Marker runoff, and all Chrome colors apply the same profile semantics at boundaries.
- Compatibility: baseline screenshots/pixel checks for every existing surface with no map; undo, clear, active stroke replay, surface resize, DPR changes, and PNG export.
- Performance/memory: measure upload/replay and sustained Marker/Spray at representative 1920×1080 and 3240×1080 logical sizes, including high-DPR backing buffers and Chrome.
